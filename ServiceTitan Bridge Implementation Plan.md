# ServiceTitan Bridge implementation plan

A production-ready blueprint for connecting Muse/Jarvis, Gus, and approved internal applications to ServiceTitan without exposing ServiceTitan credentials or requiring a front end.

**Primary implementation instruction:** Build a standalone, headless, API-only service. The ServiceTitan OAuth app will be granted full access (read/write/all scopes) to simplify onboarding, while strict access control and limitations will be enforced entirely by the Bridge API's own capability system.

**Key ownership rule:** The bridge API key is generated by the bridge owner, not by ServiceTitan or Vercel. Store one copy in Vercel and the matching copy in Muse through its secure credential flow. Never give Muse the four ServiceTitan credentials.

## How an AI coding agent should use this file

1. Treat the architecture, security boundaries, explicit non-goals, and acceptance criteria as requirements.
2. Do not invent ServiceTitan endpoint paths, request fields, statuses, or scopes. Resolve them from the current official OpenAPI specification and validate them in ServiceTitan Integration.
3. Do not build a generic proxy or accept caller-controlled upstream hosts, paths, methods, tenants, or ServiceTitan headers.
4. Do not enable production writes until every release gate in this plan passes.
5. When a tenant-specific requirement is unresolved, stop at the documented validation step rather than guessing.

## The bridge does not need a front end

#### Direct answer

The API key that Muse uses is **not issued by ServiceTitan or Vercel**. The bridge owner generates it locally with a cryptographically secure random-number generator, stores the same value as a secret environment variable in Vercel, and saves it in Muse through the Secure Vault connection flow. The key is simply a shared machine credential between Muse and the bridge.

### Provisioning is administrative, not visual

A front end is only needed if humans must sign in, configure tenants, rotate keys, or inspect logs through a web page. None of that is required for the first version. Initial setup can be completed through:

- the ServiceTitan Developer Portal for the ServiceTitan app and scopes;
- the Vercel project settings for server-side secrets;
- a local Node.js command for bridge-key generation; and
- Muse's protected credential-entry flow for the client copy of that key.

Do not build a public `/generate-key` endpoint. It creates a second authentication problem and unnecessary attack surface.

### What the bridge owns

- Authenticate Muse/Gus using a bridge-only API key.
- Translate narrow, typed routes into ServiceTitan calls.
- Acquire and cache 15-minute ServiceTitan access tokens.
- Add the required ServiceTitan app key and tenant path.
- Reject unapproved operations before they reach ServiceTitan.
- Back off on rate limits and return useful, sanitized errors.
- Log metadata and audit events, never secrets or customer payloads.

**Note:** **Recommended shape:** one private Git repository, one API-only TypeScript project, deployed as Vercel Functions. The underlying ServiceTitan app will have full read/write scopes, but the Bridge API will start with a read-only production policy and only explicitly expose write routes (like draft-estimate creation) through its own strict capability checks.

## One headless service, three trust zones

**Flow:** **Trusted caller**: Muse/Jarvis / Gus later / Internal apps --> **Bridge API**: Authenticate / Validate / Authorize / Transform --> **ServiceTitan**: OAuth server / Resource APIs / Tenant data

### Deployment boundary

The bridge is its own deployable service. It is not a page inside Engage, not JavaScript embedded in the Firebase calculator, and not a general reverse proxy. A browser-only Firebase app cannot safely hold the ServiceTitan client secret because shipped JavaScript is visible to users. The bridge must execute on a server runtime.

#### Inside the repository

- API routes and schemas
- Bridge-key authentication
- ServiceTitan token manager
- ServiceTitan adapters
- Policy checks and audit events
- OpenAPI contract and tests

#### Outside the repository

- ServiceTitan credentials
- Bridge client key values
- Production customer data
- Muse Secure Vault records
- Vercel deployment permissions

### Recommended topology

Use one repository and two isolated deployments: an **integration bridge** pointing only at ServiceTitan Integration, and a **production bridge** pointing only at production. Separate Vercel projects are the safest configuration because a preview deployment can never accidentally inherit production credentials. A single Vercel project with environment-scoped variables is acceptable only if the team rigorously prevents production secrets from entering preview builds.

**Note:** **No database is required for read-only v1.** A durable store becomes strongly recommended when write idempotency, per-client key records, or a compliance-grade audit trail is enabled.

## Threat boundaries determine the design

### Assets to protect

| Asset | Exposure impact | Storage rule |
| --- | --- | --- |
| ST client secret | Can mint access tokens | Vercel server env only |
| ST app key | Identifies integration | Vercel server env only |
| ST access token | Temporary tenant access | Memory only; never logs |
| Bridge API key | Invokes allowed bridge actions | Vercel + caller vault |
| Customer/job data | Business and personal data | Response only; minimal logs |

### Principal threats and countermeasures

- **Arbitrary proxy abuse:** Caller supplies a URL or upstream path. Countermeasure: map route names to hard-coded ServiceTitan adapters. Never accept host, module, path, method, or headers from the caller.
- **Credential leakage:** Secrets land in logs, Git, errors, or browser code. Countermeasure: server-only env vars, log redaction, secret scanning, no frontend bundle.
- **Overpowered writes:** An assistant sells, sends, dispatches, or collects money. Countermeasure: no such route exists in the Bridge API; while the ServiceTitan app has full scopes, the Bridge strictly controls the exposed operations.
- **Duplicate estimate:** A timeout causes a repeated create request. Countermeasure: idempotency key plus a durable write ledger before production writes.
- **Cross-environment mistake:** Integration traffic reaches production. Countermeasure: isolated projects, fixed base URLs, startup assertion, environment in every audit event.
- **Data overexposure:** Huge ServiceTitan responses are passed to an assistant. Countermeasure: canonical response schemas, field allowlists, pagination limits.

### Security objective

Compromise of a bridge client key must expose only the bridge's narrow route set, never the underlying ServiceTitan credentials and never operations outside the approved policy. Because the ServiceTitan app is provisioned with full read/write access, the Bridge API authorization is the primary and most critical security boundary.

## Four ServiceTitan values are not the bridge key

### Credential layers

- **Layer 1 · ServiceTitan app identity:** `ST_APP_KEY` Generated when an app is registered in the ServiceTitan Developer Portal. ServiceTitan identifies the app with this key. Official documentation says the app key is not environment-specific [2].
- **Layer 2 · Tenant OAuth identity:** `ST_CLIENT_ID` · `ST_CLIENT_SECRET` · `ST_TENANT_ID` The tenant admin approves the app's declared scopes and provides the tenant-specific OAuth credentials. Client ID/secret are environment-specific; the tenant ID is placed in resource paths [1][2].
- **Layer 3 · Bridge client identity:** `BRIDGE_API_KEY` Created by your developer. Vercel and ServiceTitan do not issue it. Muse presents it only to the bridge. It has no meaning to ServiceTitan.

### Source of each value

| Value | Who creates it | Where it belongs |
| --- | --- | --- |
| ST app key | ServiceTitan portal | Vercel only |
| ST client ID | ServiceTitan tenant connection | Vercel only |
| ST client secret | ServiceTitan tenant connection | Vercel only |
| ST tenant ID | ServiceTitan tenant/admin | Vercel only |
| Bridge API key | Your local CSPRNG script | Vercel + Muse vault |

**Warning:** **Never paste the four ServiceTitan values into Muse.** Muse receives only a bridge key. The bridge exchanges the OAuth credentials for a short-lived access token and adds the ServiceTitan app key itself.

## Generate the bridge key locally in one command

### Recommended format

Use a recognizable prefix plus 32 random bytes encoded as base64url:

```text
stb_live_<43 base64url characters>
stb_test_<43 base64url characters>
```

Thirty-two random bytes provide 256 bits of entropy. The prefix is not secret; it prevents operators from confusing test and production credentials.

### One-time Node.js generator

```typescript
node -e "const {randomBytes}=require('node:crypto');
const env=process.argv[1]||'test';
console.log('stb_'+env+'_'+randomBytes(32).toString('base64url'))" live
```

1. Run the command on a trusted local machine. Do not run it in an online code playground.
2. Copy the output once into Vercel as `BRIDGE_API_KEY`. Mark the production value sensitive and scope it only to the production deployment.
3. Copy the same raw value into Muse's secure credential-entry form when the bridge skill/connector asks for its API key. Do not paste it into chat.
4. Delete temporary clipboard/history material when practical. The committed repository contains only the variable name, never the value.

### Do not use

- `Math.random()`
- a UUID as the only secret
- a memorable phrase
- the ServiceTitan app key
- the same key for test and production
- a key committed in `.env`, source, docs, screenshots, or CI logs

**Note:** **Optional hardening:** store a SHA-256 digest of the bridge key in Vercel instead of the raw key. The server hashes the presented key and compares fixed-length digests. This limits disclosure if an environment value is viewed, while preserving simple API-key authentication.

## Muse connects through an API contract, not a web page

### Connection package

The bridge exposes an OpenAPI description containing the production base URL, operation names, request/response schemas, and an API-key security scheme. The Muse-side ServiceTitan skill calls these operations and asks the user for a credential through a secure vault setup flow.

```yaml
components:
  securitySchemes:
    BridgeApiKey:
      type: apiKey
      in: header
      name: X-Bridge-Key
security:
  - BridgeApiKey: []
```

### What happens at runtime

**Flow:** **Muse tool call**: Named bridge operation --> **Credential injection**: Vault adds X-Bridge-Key --> **Bridge verifies key**: Then calls ServiceTitan

### Provisioning checklist

- Deploy bridge and record its HTTPS base URL.
- Publish the bridge OpenAPI contract with no secrets in it.
- Configure the Muse skill to use API-key auth in `X-Bridge-Key`.
- Open the secure credential-entry flow and enter the raw bridge key.
- Verify `GET /v1/whoami` returns only client ID, environment, and allowed capability names.
- Verify a wrong key returns the same generic 401 response regardless of key length or prefix.

**Warning:** **Muse-specific boundary:** do not invent or hard-code a dashboard path. The exact skill packaging/setup screen should follow Muse's current developer tooling. The durable contract is simply base URL + header name + secret value.

### Recommended stack

Node.js 20+ with TypeScript, Vercel Functions, Zod for runtime schemas, Vitest for unit and integration tests, and native `fetch`/`node:crypto`. A full front-end framework is optional. If Next.js is used for packaging convenience, do not create pages or public assets.

```text
servicetitan-bridge/
├─ api/
│  └─ v1/[...route].ts        # one serverless entry point
├─ src/
│  ├─ config.ts               # fail-fast env validation
│  ├─ auth/bridge-key.ts      # caller authentication
│  ├─ servicetitan/
│  │  ├─ token-manager.ts
│  │  ├─ client.ts
│  │  └─ routes.ts            # hard-coded upstream mapping
│  ├─ policy/
│  │  ├─ capabilities.ts
│  │  └─ draft-estimate.ts
│  ├─ schemas/                # Zod request/response schemas
│  ├─ observability/
│  └─ http/
├─ openapi/bridge.openapi.yaml
├─ scripts/generate-bridge-key.mjs
├─ test/
├─ vercel.json
├─ package.json
└─ README.md
```

### Why one function entry point

- Shared authentication, request limits, correlation IDs, and redaction are applied once.
- Cold-start token caches are reused across routes within the same warm instance.
- A central router makes it easier to prove that every public operation is allowlisted.
- The code remains portable to another Node host if Vercel no longer fits.

**Note:** **Do not expose a route such as** `POST /proxy` **with arbitrary method/path/body fields.** That design defeats the allowlist and makes every ServiceTitan scope reachable through one mistake.

### Environment variables

| Name | Required | Rule |
| --- | --- | --- |
| ST_ENVIRONMENT | Yes | integration \| production |
| ST_CLIENT_ID | Yes | Server-only secret |
| ST_CLIENT_SECRET | Yes | Server-only secret |
| ST_APP_KEY | Yes | Server-only secret |
| ST_TENANT_ID | Yes | Digits only; fixed tenant |
| BRIDGE_API_KEY | Yes | Expected prefix + minimum length |
| WRITE_MODE | Yes | off \| draft_estimates |
| LOG_LEVEL | No | info in production |
| UPSTREAM_TIMEOUT_MS | No | 8,000 default |

### Fail-fast invariants

```text
if (ST_ENVIRONMENT === 'production') {
  assert(API_BASE === 'https://api.servicetitan.io');
  assert(AUTH_URL === 'https://auth.servicetitan.io/connect/token');
  assert(BRIDGE_API_KEY.startsWith('stb_live_'));
}
if (ST_ENVIRONMENT === 'integration') {
  assert(API_BASE === 'https://api-integration.servicetitan.io');
  assert(AUTH_URL === 'https://auth-integration.servicetitan.io/connect/token');
  assert(BRIDGE_API_KEY.startsWith('stb_test_'));
}
assert(/^\d+$/.test(ST_TENANT_ID));
```

Base URLs should be selected from code by the environment enum, not accepted as free-form environment variables. That prevents server-side request forgery and typographical routing mistakes.

### Vercel setup

- Production project receives only production values.
- Integration project receives only integration values.
- No ServiceTitan secret is prefixed with `NEXT_PUBLIC_`.
- After any secret change, create a new deployment; Vercel changes do not alter previous deployments [5].
- Limit project access to the smallest developer group that needs to deploy or rotate credentials.

## Every request follows the same guarded pipeline

1. Assign request ID
2. Reject oversized request
3. Authenticate bridge key
4. Match exact route
5. Validate schema
6. Authorize capability
7. Acquire ST token
8. Call fixed upstream path
9. Map/redact response
10. Emit audit metadata

### Middleware order is part of the security model

1. **Method and route check:** unknown routes return 404 before any ServiceTitan call.
2. **Body limit:** reject bodies above 128 KB; most bridge requests should be far smaller.
3. **Authentication:** require exactly one bridge-key header.
4. **Rate limit:** enforce per client key and route class.
5. **Content type:** writes require `application/json`.
6. **Schema validation:** strip unknown fields or, preferably, reject them.
7. **Policy:** read/write mode and capability must authorize the operation.
8. **Execution:** adapter selects a compile-time ServiceTitan path.
9. **Response shaping:** return canonical fields, not raw upstream objects by default.

### Correlation

Accept an optional `X-Request-Id` only if it matches a conservative format; otherwise generate a UUID. Return it in every response. Never use a secret, customer ID, phone number, or ServiceTitan trace ID as the bridge request ID.

**Note:** **Core rule:** authenticate once, authorize every operation, validate both directions, and make the upstream destination impossible for the caller to choose.

## Compare bridge keys in constant time

### Reference middleware

```typescript
import { createHash, timingSafeEqual } from 'node:crypto';

function digest(value: string): Buffer {
  return createHash('sha256').update(value, 'utf8').digest();
}

export function authenticate(req: Request): void {
  const presented = req.headers.get('x-bridge-key') ?? '';
  const expected = process.env.BRIDGE_API_KEY ?? '';

  const ok = timingSafeEqual(digest(presented), digest(expected));
  if (!ok || expected.length === 0) {
    throw new HttpError(401, 'AUTHENTICATION_FAILED',
      'Valid bridge credentials are required.');
  }
}
```

Hashing both strings first guarantees equal-length buffers for `timingSafeEqual`. Node documents that the primitive uses a constant-time algorithm, while warning that surrounding code must also avoid introducing timing leaks [6].

### Response behavior

- Missing and invalid keys return the same status, body shape, and headers.
- Do not reveal whether a key prefix, length, client identity, or environment matched.
- Do not echo the presented key.
- Return `Cache-Control: no-store`.
- Count failures by a privacy-preserving source identifier and alert on bursts.

### Multiple clients

Give Jarvis and Gus different keys once both are active. Associate each key with a stable client ID and capability set. In v1 this can be a sensitive JSON environment value; when the list grows, move key digests and status to a durable store. Separate keys allow targeted revocation and audit without interrupting other clients.

**Warning:** **Never identify a caller solely by IP.** Server-to-server egress addresses may change or be shared. IP controls can supplement a key, but should not replace it.

## Hide the 15-minute token lifecycle

### Verified vendor behavior

ServiceTitan supports the OAuth 2.0 client-credentials flow for machine-to-machine access. The token response includes `expires_in: 900`; ServiceTitan says tokens expire in 15 minutes, no refresh token is issued, and clients should cache tokens rather than request one for every transaction [1][3].

### Token-manager requirements

- POST form-encoded `grant_type=client_credentials`, client ID, and client secret.
- Cache the token only in process memory.
- Calculate expiry from the response; refresh 60 seconds early.
- Use a single in-flight promise so concurrent requests share one token fetch.
- On a resource 401, invalidate once, fetch once, and replay once.
- Never log the token response or authorization header.
- Do not write tokens to Supabase, files, build cache, or browser storage.

```typescript
let cached: { value: string; expiresAt: number } | undefined;
let inFlight: Promise<string> | undefined;

export async function getToken(): Promise<string> {
  if (cached && Date.now() < cached.expiresAt - 60_000) {
    return cached.value;
  }
  if (inFlight) return inFlight;
  inFlight = fetchToken().then(({ access_token, expires_in }) => {
    cached = { value: access_token,
      expiresAt: Date.now() + expires_in * 1000 };
    return access_token;
  }).finally(() => { inFlight = undefined; });
  return inFlight;
}
```

**Note:** **Serverless nuance:** each warm Vercel instance has its own memory cache. Multiple cold instances may independently fetch tokens; that is acceptable. The single-flight guard prevents a burst within one instance. Do not add a database merely to share a 15-minute token.

## Pin hosts, headers, timeouts, and schemas

### Upstream request construction

```typescript
const hosts = {
  integration: 'https://api-integration.servicetitan.io',
  production: 'https://api.servicetitan.io'
} as const;

async function stRequest<T>(route: StRoute, input: unknown): Promise<T> {
  const token = await getToken();
  const { method, path, query, body, responseSchema } =
    buildKnownRoute(route, input); // no caller URL

  const response = await fetch(hosts[config.environment] + path, {
    method,
    headers: {
      'Authorization': token,
      'ST-App-Key': config.appKey,
      'Accept': 'application/json',
      ...(body ? {'Content-Type': 'application/json'} : {})
    },
    body: body ? JSON.stringify(body) : undefined,
    signal: AbortSignal.timeout(config.upstreamTimeoutMs)
  });
  return parseUpstream(response, responseSchema);
}
```

### Important protocol details

- The official first-call example sends the access token directly in `Authorization`, alongside `ST-App-Key` [1]. Implement the current official form and lock it with an integration contract test rather than guessing.
- The Sales & Estimates OpenAPI server path is `/sales/v2`, even though the specification identifier is `tenant-salestech-v2` [4]. Build paths from each specification's `servers` block.
- The tenant ID belongs in the path and is always taken from server configuration, never a caller parameter.
- Encode query parameters with `URLSearchParams`; never concatenate raw input into a path.
- Set connect/response timeouts. Vercel Functions have bounded execution time [7].

**Warning:** **Do not forward caller headers.** Construct the upstream header set from scratch. In particular, drop Host, Authorization, X-Bridge-Key, cookies, forwarding headers, and any user-supplied ST-App-Key.

## Versioned routes expose business operations, not ServiceTitan

### Contract rules

- Prefix all public operations with `/v1`.
- Use nouns and business intent: `/estimate-drafts`, not `/sales/v2/tenant/...`.
- Use stable canonical IDs and ISO 8601 UTC timestamps.
- Return money as decimal strings or integer cents; do not rely on binary floating point.
- Default and maximum page sizes are enforced server-side.
- Reject unknown fields on write payloads.
- Every operation declares a capability such as `customers:read` or `estimates:draft:create`.

### Standard envelope

```json
{
  "data": { ... },
  "meta": {
    "requestId": "018f...",
    "environment": "integration",
    "nextPage": null
  }
}
```

### Health and identity

| Route | Auth | Contents |
| --- | --- | --- |
| GET /healthz | No | Process alive only |
| GET /readyz | Internal or key | Config valid; no live ST call |
| GET /v1/whoami | Yes | Client ID, environment, capability names |
| GET /v1/version | Yes | Build SHA, contract version |

`/healthz` must not report tenant ID, scope lists, dependency versions, environment values, or upstream connectivity. A deeper diagnostic route should require authentication and still return only safe summaries.

**Note:** **OpenAPI is the contract of record.** Generate or validate route types against it in CI. The Muse skill should call only named operations in that contract.

## The only initial write creates an estimate draft

### Public operation

```text
POST /v1/estimate-drafts
X-Bridge-Key: [stored in client vault]
Idempotency-Key: 018f...client-generated...
Content-Type: application/json
```

### Request shape

```json
{
  "jobId": "123456",
  "name": "Garage door replacement",
  "summary": "Internal draft for office review",
  "items": [
    { "skuId": "789", "quantity": "1", "unitPrice": "0.00" }
  ]
}
```

The bridge schema must not expose fields for `soldBy`, sold/dismissed status, customer signature, booking, dispatch, payment, outbound communication, or any generic custom action. The server constructs the ServiceTitan create-estimate payload and omits state-changing fields not necessary for creation.

### Required policy checks

- `WRITE_MODE` equals `draft_estimates`.
- The authenticated client has `estimates:draft:create`.
- An `Idempotency-Key` is present and well formed.
- The job, location, and referenced pricebook items exist and belong to the configured tenant.
- Quantity and price bounds pass business rules.
- The upstream response is immediately read back and its status is verified as the tenant's expected unsold/open state.
- The response includes `requiresHumanReview: true`.

**Warning:** **Release gate:** the exact default status and minimum request fields must be proven against the current ServiceTitan Integration environment and pinned in tests. The public docs show create and update operations, but tenant configuration can affect behavior. Do not enable production writes until this is verified.

## Canonical schemas keep callers and ServiceTitan decoupled

### Input principles

- Use strings for external identifiers even if ServiceTitan currently models some as 64-bit integers.
- Trim text, cap lengths, reject control characters, and normalize phone/email only where search requires it.
- Reject unknown keys on every write object.
- Represent quantities and money with decimal-safe validation.
- Validate IDs against `^[1-9][0-9]{0,18}$` unless the live specification proves another format.
- Never accept a tenant ID, host, upstream URL, authorization token, or app key from request input.

### Response minimization

#### Return by default

- stable ID and display name
- business status
- relevant dates
- totals needed for the operation
- location/customer reference IDs
- pagination cursor/page metadata

#### Omit by default

- internal audit/user stamps
- full contacts when not requested
- free-form notes
- attachments and recordings
- unrelated custom fields
- upstream trace details

### Schema ownership

Keep two schema layers: **vendor schemas** generated or copied from the pinned ServiceTitan OpenAPI version, and **bridge schemas** designed for callers. A mapper converts between them. This prevents an upstream field addition from silently entering the assistant's context and prevents an upstream rename from breaking every client.

**Note:** **Contract drift:** run a scheduled or manual OpenAPI diff during maintenance. Treat new required fields, removed fields, enum changes, and server-path changes as breaking until reviewed.

## Idempotency is mandatory before production writes

### Why an idempotency ledger is needed

After a create request is sent, the bridge may lose the response. Retrying blindly can create a duplicate estimate. In-memory state cannot solve this on serverless infrastructure because another instance may receive the retry.

### Recommended durable record

```text
bridge_idempotency
- client_id        text
- operation        text
- idempotency_key  text
- request_hash     text
- status           pending | succeeded | failed
- response_code    integer
- response_body    jsonb      # minimal canonical result
- created_at       timestamptz
- expires_at       timestamptz
UNIQUE (client_id, operation, idempotency_key)
```

### Algorithm

1. Hash the canonical validated request.
2. Atomically insert `pending` under the client/operation/key tuple.
3. If the tuple already exists with a different hash, return 409.
4. If it already succeeded, replay the stored canonical result.
5. If it is pending, return 409/202 and require reconciliation; do not launch a second create.
6. Call ServiceTitan once and store the resulting estimate ID/status.
7. On an ambiguous timeout, keep the record pending and reconcile by searching the target job plus a unique marker added to the summary or external link, if the ServiceTitan schema and business policy permit that marker.

### Storage choice

A dedicated Supabase project is cleanest if strict standalone isolation matters. Reusing Engage's Supabase is technically possible but couples availability and permissions. If production writes are deferred, ship read-only without a database, then add the ledger as the prerequisite for enabling `WRITE_MODE=draft_estimates`.

**Warning:** **Do not automatically retry POST after a network timeout** unless the idempotency/reconciliation path is proven. A timeout does not prove ServiceTitan failed to create the record.

## Retry reads carefully and stop on sustained throttling

### Retry policy

| Condition | Read | Write |
| --- | --- | --- |
| 429 | Honor Retry-After; bounded retry | Only if not sent or idempotent |
| 502/503/504 | Up to 2 retries with jitter | No blind retry |
| Network timeout | Up to 1 retry | Ambiguous; reconcile |
| 401 | Refresh token once | Refresh once before sending again only if safe |
| 400/403/404 | No retry | No retry |

### Backoff

```text
delay = Retry-After when valid;
otherwise delay = random(0, min(cap, base * 2 ** attempt));
base = 500 ms; cap = 8,000 ms; attempts = 2;
```

Do not hard-code an assumed ServiceTitan requests-per-second limit unless ServiceTitan provides a tenant/app-specific value. Design from observed 429 responses. If the required delay would consume the Vercel function's remaining execution budget, return a sanitized 503 with `retryAfterSeconds` rather than sleeping until the function is killed.

### Bridge-side protection

- Per-client request budget with stricter limits for writes.
- Maximum concurrent ServiceTitan calls per function instance.
- No automatic traversal of unlimited pages.
- Circuit breaker after a burst of upstream 429/5xx responses.
- Return `Retry-After` to the caller when known.
- Never retry authentication failures caused by bad credentials in a tight loop.

**Note:** **Operational rule:** a 429 is a stop signal for that burst. Back off, preserve the request ID, and expose the delay to the caller.

## Return stable errors without leaking upstream internals

### Canonical error

```json
{
  "error": {
    "code": "UPSTREAM_RATE_LIMITED",
    "message": "ServiceTitan is temporarily rate limiting requests.",
    "retryable": true,
    "retryAfterSeconds": 8,
    "requestId": "018f..."
  }
}
```

### Status mapping

| Bridge status | Code | Meaning |
| --- | --- | --- |
| 400 | INVALID_REQUEST | Schema or business rule failed |
| 401 | AUTHENTICATION_FAILED | Bridge key missing/invalid |
| 403 | CAPABILITY_DENIED | Known client lacks operation |
| 404 | NOT_FOUND | Bridge route or record absent |
| 409 | IDEMPOTENCY_CONFLICT | Key reused with different body |
| 429 | BRIDGE_RATE_LIMITED | Bridge throttled caller |
| 502 | UPSTREAM_INVALID_RESPONSE | ServiceTitan contract mismatch |
| 503 | UPSTREAM_UNAVAILABLE | Temporary upstream failure |

### What stays server-side

Store the upstream HTTP status, ServiceTitan trace identifier, and sanitized diagnostic category in structured logs. Do not return upstream stack traces, raw error bodies, token errors, internal paths, tenant identifiers, environment values, or dependency versions to an unauthenticated caller.

**Note:** **Developer ergonomics:** in Integration only, an authenticated diagnostic flag may return a small set of field-level validation messages. It must still redact values and must never be enabled in production.

For each draft creation, record the authenticated client ID, operation, idempotency key digest, request hash, resulting estimate ID, resulting status, request ID, deployment version, timestamp, and outcome. ## Defense in depth keeps one leaked key from becoming full access

### Controls by layer

#### ServiceTitan

- Grant full read/write scopes to the ServiceTitan app to prevent constant reconfiguration.
- The burden of restricting payment, dispatch, payroll, or messaging writes is fully delegated to the Bridge API.
- Restrict app visibility to the intended tenant.

#### Vercel

- Sensitive environment variables.
- Separate integration/production projects.
- Protected production branch.
- Minimum project membership.
- Optional WAF/rate controls.

#### Application

- Constant-time key comparison.
- Explicit route/capability map.
- Strict schemas and body caps.
- Fixed upstream hosts.
- No secret logging.

#### Operations

- Per-client keys.
- Quarterly rotation target.
- Immediate revocation runbook.
- Dependency and secret scanning.
- Write audit review.

### HTTP hardening

- HTTPS only; redirect or reject plain HTTP at the platform edge.
- `Cache-Control: no-store` on all authenticated responses.
- `X-Content-Type-Options: nosniff`.
- Restrictive CORS; server-to-server callers do not need broad browser origins.
- Reject unexpected content encodings and unsupported methods.
- Bound JSON depth, array length, text length, and total body size.

### Secret scanning

CI must scan commits for key prefixes and common ServiceTitan variable names. Add `.env*` to `.gitignore`, but do not rely on ignore rules alone. A secret committed once must be rotated even if the commit is later deleted.

## Tests prove policy before live data is touched

### Unit suite

- **Key auth:** correct, missing, malformed, wrong, and long inputs; identical public failure shape.
- **Config:** environment/host/key-prefix invariants; missing or malformed variables fail startup.
- **Token manager:** cache hit, early refresh, single-flight, token error, 401 invalidation.
- **Router:** every route maps to one fixed method/path; unknown method/path rejected.
- **Schemas:** boundary values, unknown fields, oversized arrays, decimal handling.
- **Policy:** write mode off; missing capability; forbidden fields; production guard.
- **Retry logic:** Retry-After seconds/date, jitter cap, no unsafe POST replay.
- **Redaction:** secrets and PII absent from logs/errors under success and failure.

### Contract suite

- Mock ServiceTitan server verifies exact headers, form encoding, tenant path, method, and body.
- Captured vendor fixtures are sanitized before commitment.
- Bridge OpenAPI validates every request and response example.
- Snapshot tests ensure forbidden public operations never appear in the OpenAPI document.

### Integration environment suite

- Acquire a real 900-second token.
- Call one harmless settings/read endpoint.
- Exercise pagination and modified-date filtering.
- Create an estimate against a dedicated test job.
- Read it back and verify exact initial status.
- Repeat the same idempotency key and prove no duplicate.
- Verify no customer communication, sale, booking, or dispatch occurred.

**Warning:** **Never run destructive or state-changing integration tests against production.** Production smoke tests are read-only unless a human explicitly authorizes a specific test record and cleanup procedure.

## CI/CD blocks secret leaks and unsafe scope expansion

### Pull-request pipeline

1. Install locked deps
2. Lint + typecheck
3. Unit tests
4. OpenAPI validation
5. Secret scan
6. Dependency audit
7. Preview deploy
8. Integration smoke

### Production controls

- Protect `main`; require at least one review by the code owner.
- Require test status checks before merge.
- Pin the Node major version and commit the package lockfile.
- Do not expose secrets to pull requests from untrusted forks.
- Use a production deployment approval if available.
- Include build SHA in authenticated diagnostics and audit events.
- Retain the previous known-good deployment for fast rollback.

### Deployment order

1. Create the integration Vercel project and add integration credentials.
2. Deploy with `WRITE_MODE=off`.
3. Run integration read tests.
4. Provision a test bridge key to the Muse development connection.
5. Enable draft writes only after the idempotency store and write tests pass.
6. Create the production project with production credentials and a different bridge key.
7. Deploy production read-only; run a safe smoke test.
8. Enable production draft writes through a reviewed configuration change.

**Note:** **Vercel behavior:** environment-variable updates apply to new deployments, not already-created deployments [5]. Rotation and configuration changes therefore include a redeploy step.

## Stage capability in four reversible releases

### Release 0 · Local and mocked

All policy, auth, schema, retry, and redaction tests pass against a fake upstream. No ServiceTitan credentials are required in CI.

### Release 1 · Integration read-only

Connect to ServiceTitan Integration with read scopes only. Verify token acquisition, each allowlisted route, pagination, and canonical mapping. Use synthetic/test tenant records.

### Release 2 · Integration draft writes

Add the estimate-write scope and durable idempotency ledger. Enable only `POST /v1/estimate-drafts`. Confirm the resulting estimate remains in the intended unsold/open state and no downstream communication or booking is triggered.

### Release 3 · Production read-only

Create isolated production credentials and a new `stb_live_` bridge key. Deploy with writes disabled. Validate one or two narrow reads against known records, then monitor authentication, 429, and latency metrics.

### Release 4 · Production draft writes

Enable the single draft capability after owner sign-off. Start with one designated operator/client key, review every write audit event for the first operating period, and keep rollback as a one-variable change: `WRITE_MODE=off` followed by redeployment.

### Go/no-go gate

**Note:** **Go only when:** endpoint scopes are verified, read mappings pass against live Integration, draft status is proven, duplicate creation is prevented, logs are clean of secrets/PII, key revocation has been rehearsed, and the owner accepts the exact production capability list.

## Rotate keys without downtime and know how to stop

### Bridge-key rotation

1. Generate a new key with the correct test/live prefix.
2. Temporarily deploy support for both old and new keys (or a current/next key set).
3. Update the Muse Secure Vault connection to the new raw key.
4. Run `/v1/whoami` and one safe read.
5. Remove the old key and redeploy.
6. Confirm old-key requests return 401; record the rotation event.

### ServiceTitan-secret rotation

Rotate through the ServiceTitan tenant/developer workflow, update Vercel, redeploy, and validate token acquisition. Never copy the new client secret into Muse. If scopes change, follow ServiceTitan's app-version and tenant-admin approval process [2].

### Emergency shutdown

- Set `WRITE_MODE=off` and deploy.
- Revoke or replace the affected bridge key.
- If upstream credentials may be exposed, rotate the ServiceTitan client secret/app connection.
- Review authentication failures, write audit records, deployment history, and ServiceTitan activity for the incident window.
- Preserve logs without copying customer payloads into the incident document.

### Routine checks

| Cadence | Check | Owner action |
| --- | --- | --- |
| Weekly | 429/5xx and write audit | Investigate trend |
| Monthly | Dependencies and scopes | Patch/review |
| Quarterly | Bridge-key rotation | Rotate/revoke |
| On API release | OpenAPI diff | Contract review |

## Known assumptions and decisions still required

### Verified assumptions

- ServiceTitan uses OAuth client credentials, issues 900-second access tokens, and recommends caching [1][3].
- Resource calls require the access token and `ST-App-Key` [1].
- ServiceTitan app registration supports tenant IDs and granular read/write scopes [2].
- The Sales & Estimates specification exposes production and integration servers under `/sales/v2` and separate read/write scopes [4].
- Vercel Functions can read sensitive configuration from environment variables and execute in an isolated server runtime [5][7].

### Must be confirmed before coding the production write

- The exact ServiceTitan scopes approved for Grand Valley Garage Doors.
- The current tenant's minimum fields and default status for estimate creation.
- Whether price overrides are permitted or every item must use the tenant pricebook value.
- Which ServiceTitan job/location fields are required by office workflow.
- The desired production retention period for write audit and idempotency records.
- Whether Jarvis and Gus receive identical or different capabilities. Different keys are recommended either way.
- The current Muse skill publishing/configuration workflow for an API-key-secured OpenAPI service.

### Deliberate non-goals for v1

No human login UI, tenant self-service onboarding, arbitrary ServiceTitan pass-through, webhooks, background synchronization, customer messaging, estimate sale/dismissal, job booking, dispatch, payments, payroll, pricebook mutation, or multi-tenant public SaaS support.

**Note:** **Recommended first production capability:** read customer/job/estimate/pricebook context. Draft estimate creation comes second and remains subject to explicit human review outside the bridge.
